Events and input

Input reaches a program as events: four-byte records in a queue that the host fills at the start of each frame and the program empties with the system device's next_event call. Keys, typed text, the pointer and the wheel come from the user; other events are answers from devices (content requests, page layout) and, for the shell of a system, news about its machines. Game controllers are not events: their state is read with the controller call. This article lists every event and the controller state byte by byte.

The queue

  • The queue holds at most 64 events. An event that arrives when it is full is dropped; the program is not told.
  • At the start of each frame the host appends that frame's input events, in the order they happened, then the content-done events of the requests completed in that frame.
  • At most one feeds-updated event is queued per frame; a second one in the same frame's input is dropped.
  • The two page located events (0Dh, 0Eh) are queued together or not at all: if the queue has room for only one, neither is queued.
  • Events stay in the queue across frames until the program reads them. The queue is part of the machine's state.

next_event (101h) takes a0 = a 4-byte buffer in RAM. It removes the head event, writes type, a, b, c in that order, and returns 1; if the queue is empty it writes nothing and returns 0. In C:

terse_event e;                 /* fields: type, a, b, c */
while (terse_event_pop(&e) != EV_NONE)
    handle(&e);                /* EV_NONE is 0: queue empty */

Keys

Key down and key up carry the key's USB HID keyboard usage ID: the physical key, whatever the keyboard layout. Use text events for the characters a user types.

The modifiers byte b has bit 0 Shift, bit 1 Control, bit 2 Alt and bit 3 Meta (MOD_SHIFT, MOD_CONTROL, MOD_ALT, MOD_META); the other bits are zero.

A host may keep some keys for itself. In a system the home key (F12 in terse-host) is never delivered to any machine; with a single machine there is no home key. While the host shows a consent prompt the keyboard is the host's. A host may keep a few more (terse-host keeps Ctrl+Alt with minus, equals or M for its volume); such a key's press and its release reach no program, though the modifier keys held with it do. A paste key is not kept: see below.

While a key is held a host may repeat it: more key-down events for the same key, each followed by the text it types, with no key-up between them, and one key-up at the end. So a key-down for a key that is already down is a repeat.

Text

A text event carries one Unicode scalar value (up to 21 bits) produced by the host's text input, after the keyboard layout and input-method composition: a is bits 0-7, b bits 8-15 and c bits 16-20. In terse-host a key that types a character gives a key down, then a text event. No host sends a text event for a control character: Enter, Tab, Backspace, Escape and Ctrl+letter give only their keys.

uint32_t cp = e.a | (uint32_t)e.b << 8 | (uint32_t)e.c << 16;

Text the user pastes arrives the same way, one event per character, no faster than the queue has room for, to whichever machine has the focus as it is sent. A CR LF pair or a lone CR becomes U+000A; tabs (U+0009) and U+000A are kept, other control characters dropped. The paste key itself (terse-host: Ctrl+V or Shift+Insert) arrives as a key and brackets the paste: its key down before the text, its key up after the last of it, even if the user let go sooner. So a program can tell a paste from typing: a spreadsheet pastes its own copied cells instead, or splits the text at tabs and line breaks into cells. A paste key with nothing to paste still sends its key down and key up.

Pointer

Positions are in screen units: x from 0 to 639, y from 0 to 479, (0, 0) at the top left. A pointer event is sent when the position or a button changes, at most once per frame for movement; a button change is sent at once, with the current position. Positions outside the screen are clamped to it, and nothing is sent when the pointer leaves the host's window.

The macros of terse.h decode it:

if (e.type == EV_POINTER) {
    uint32_t x = EV_POINTER_X(e);       /* 0-639 */
    uint32_t y = EV_POINTER_Y(e);       /* 0-479 */
    uint8_t buttons = EV_POINTER_BUTTONS(e);
    if (buttons & BUTTON_PRIMARY)
        press(x, y);
}

EV_POINTER_BUTTONS gives the three button bits shifted down to bits 0-2, where BUTTON_PRIMARY (1), BUTTON_SECONDARY (2) and BUTTON_MIDDLE (4) test them. A button that was pressed is detected by comparing with the buttons of the previous pointer event. A terminal cell under the pointer is column x / 8, row y / 16.

Wheel

a is the vertical steps and b the horizontal steps, each a signed byte from −127 to 127 (read them as (int8_t)e.a). A positive vertical step means scroll down, towards later content; a positive horizontal step means scroll right. At most one wheel event is sent per frame; the host adds up smaller movements until they make a whole step.

Answers from devices

  • Content done (05h): content request a (1 to 8) has completed with status b. It is queued in the frame in which the host completes the request; if the queue is full it is dropped, but the request block in RAM is still updated, so a program can also look at the block.
  • Feeds updated (07h): the host stored new feed entries since the previous frame. It is sent after the automatic download of those entries' articles has finished or failed; the download of a program's image is announced by a feeds-updated event of its own when it ends.
  • Page laid out (08h): the page document's laid-out height in screen units, 24 bits (FFFFFFh if larger); EV_PAGE_HEIGHT(e) decodes it.
  • Page anchor (09h): a button was pressed over text or a figure with anchor id a + 256 × b (EV_ANCHOR_ID(e)); c holds the buttons in bits 3-5, the same bits as a pointer event's (EV_ANCHOR_BUTTONS(e)), its other bits 0. It follows the pointer event of the same press.
  • Page located (0Dh) and page located y (0Eh): the answer to the page's locate, always as this pair. 0Dh gives the anchor id and the height of its line (255 if larger); 0Eh gives the line's y from the top of the document in 24 bits. An anchor not found gives height 0 and y FFFFFFh. page_place_event in terse.h collects the pair.

The page device's article has the exact rules for its events.

Input in a system

In a system the host's input is in the shell's screen units, and each frame it is routed before the shell runs:

InputGoes to
Key down, key up, text, wheelthe machine with the focus if it is running; the shell if the focus is 0; otherwise nobody
Pointer over a machine's picturethat machine (the highest handle where pictures overlap), mapped into its screen units, if it is running; otherwise nobody
Pointer over no picturethe shell, unchanged
Controllersthe machine with the focus (the shell if it is 0); every other machine reads all four as not connected
Content done, feeds updated, page eventseach machine its own
Anything else in the host's inputthe shell, unchanged

The focus that routes a frame's input, controllers included, is the one at routing: a home key changes it for the events after it, and a focus call takes effect at the next frame.

A position (x, y) over a picture at (px, py) of size pw × ph is mapped to x′ = ⌊(2(x − px) + 1) × 640 / (2pw)⌋ and y′ = ⌊(2(y − py) + 1) × 480 / (2ph)⌋. A pointer event that presses a button over a picture also gives the shell a machine pressed event, whatever the machine's state.

Controllers

Up to four game controllers, numbered 0 to 3. Their state is latched at the start of each frame, so it does not change within a frame. The controller call (105h, a0 = number, a1 = 8-byte buffer in RAM) writes eight bytes and returns byte 0; a number above 3 reads as not connected.

ByteContents
0bit 0: connected; other bits zero
1bits 0-7: up, down, left, right, A (bottom), B (right), X (left), Y (top)
2bits 0-7: left shoulder, right shoulder, left trigger, right trigger, select, start, left stick press, right stick press
3left stick x, signed: −127 left to 127 right
4left stick y, signed: −127 up to 127 down
5right stick x
6right stick y
7zero

A controller that is not connected reads as all zeros. Axis values are never −128. In C, terse_pad_read(n, &pad) fills a terse_pad (fields connected, buttons, buttons2, lx, ly, rx, ry), and PAD_UP ... PAD_Y test buttons, PAD_L1, PAD_R1, PAD_L2, PAD_R2, PAD_SELECT and PAD_START test buttons2.

terse_pad pad;
terse_pad_read(0, &pad);
if (pad.connected) {
    x += pad.lx / 32;
    if (pad.buttons & PAD_A)
        jump();
}

Recording and replay

Every event is an input. The events of each frame, with the Unix time, the random bytes, the controller states and the content completions, are what a host records to replay a run exactly; terse run --events <file> reads such input from a text file. Reading an event costs 4 units plus 1 for the copied record; see charges.
