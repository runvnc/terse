Make a reader in Go, step 2: fetch an article

Articles travel through relays: servers that keep blobs (any bytes, up to 1 MiB) and hand them to whoever asks. A blob's ID is its BLAKE3 hash, so whatever a relay sends, you can check that it is the blob you asked for. In this step your reader asks a relay for an article by its ID, checks it, and shows it with step 1's code.

The libraries

go.mod names the module and the libraries steps 2 and 3 use:

module reader

go 1.24.0

require (
    github.com/gorilla/websocket v1.5.3
    github.com/runvnc/terse/sdk/go v0.9.0
    lukechampine.com/blake3 v1.5.1
)

require (
    filippo.io/edwards25519 v1.2.0 // indirect
    github.com/klauspost/cpuid/v2 v2.0.9 // indirect
)
  • github.com/gorilla/websocket is the most widely used WebSocket package for Go. It has no dependencies of its own and a plain blocking interface (dial, write a message, read a message), and it answers pings and joins fragmented messages by itself, as a Tersenet client must. It speaks wss:// (over TLS, as public relays are) as well as ws://, with the system's certificate authorities.
  • lukechampine.com/blake3 is a widely used BLAKE3 for Go; blake3.Sum256 gives the 32-byte hash that is a blob's ID. It brings one small package of its own, klauspost/cpuid, to find the processor's fast instructions.
  • github.com/runvnc/terse/sdk/go is the Tersenet SDK for Go (package tersenet): step 3 checks entries with it. It brings filippo.io/edwards25519, the curve arithmetic Go's own crypto/ed25519 is built on.

go.sum, beside it, pins their exact contents. Go downloads them the first time you build.

The code

relay/relay.go gets a blob from a relay:

package relay

import (
    "encoding/binary"
    "errors"

    "github.com/gorilla/websocket"
    "lukechampine.com/blake3"
)

type ID = [IDSize]byte

const (
    IDSize         = 32
    typeGet        = 0x01
    typeGetReply   = 0x81
    requestNumber  = 1
    statusAt       = 5
    blobAt         = 6
    statusFound    = 1
    statusNotFound = 2
)

func Get(conn *websocket.Conn, id ID) ([]byte, error) {
    request := []byte{typeGet}
    le := binary.LittleEndian
    request = le.AppendUint32(request, requestNumber)
    request = append(request, id[:]...)
    err := conn.WriteMessage(websocket.BinaryMessage, request)
    if err != nil {
        return nil, err
    }
    for {
        _, reply, err := conn.ReadMessage()
        switch {
        case err != nil:
            return nil, err
        case len(reply) < blobAt || reply[0] != typeGetReply:
            continue
        case reply[statusAt] == statusNotFound:
            return nil, errors.New("the relay does not have it")
        case reply[statusAt] != statusFound:
            return nil, errors.New("the relay refused it")
        case blake3.Sum256(reply[blobAt:]) != id:
            return nil, errors.New("hash check failed")
        }
        return reply[blobAt:], nil
    }
}

fetch/main.go is the program:

// Step 2: fetch an article from a relay by its ID.
package main

import (
    "bytes"
    "encoding/hex"
    "log"
    "os"

    "github.com/gorilla/websocket"

    "reader/article"
    "reader/relay"
)

func main() {
    id, err := hex.DecodeString(os.Args[2])
    if err != nil || len(id) != relay.IDSize {
        log.Fatal("an ID is 64 hexadecimal digits")
    }
    url := os.Args[1]
    conn, _, err := websocket.DefaultDialer.Dial(url, nil)
    if err != nil {
        log.Fatal(err)
    }
    blob, err := relay.Get(conn, relay.ID(id))
    if err != nil {
        log.Fatal(err)
    }
    if bytes.HasPrefix(blob, []byte("TERS")) ||
        bytes.HasPrefix(blob, []byte("TDOC")) {
        log.Fatal("not an article")
    }
    article.Show(blob)
}

They are 49 and 35 lines; the whole program, with step 1's article package, is 161.

How it works

A relay is a WebSocket server, and every message is one binary WebSocket message; numbers in it are least significant byte first. To ask for a blob, Get sends a Get:

OffsetSizeField
01type: 01h, Get
14request number: any; the reply repeats it
532the blob's ID

It then reads messages until the Get reply comes, skipping any other (in step 3 the relay sends feed entries over the same connection):

OffsetSizeField
01type: 81h, Get reply
14the request number
51status: 1 found, 2 not found, 3 or more refused
6the restthe blob, if the status is 1

The names in the const block are these offsets and values. A status other than 1 is an error, saying which.

The hash check is the important line. Relays are not trusted, the hash is: if the BLAKE3 hash of the bytes is not the ID asked for, Get returns an error and the bytes are never shown.

main reads the relay's address and the ID, connects, and gets the blob. A blob that starts with TERS is a program and one that starts with TDOC a document: neither is an article, so neither is shown as text. Anything else it shows with article.Show.

Run it

You need a relay. terse-relay comes with every Tersenet download. In another terminal, start one of your own on port 7979, apart from the one a running Tersenet host keeps on 7878:

terse-relay --listen 127.0.0.1:7979 --store try-relay

It prints listening on ws://127.0.0.1:7979 and keeps what it is given in the folder try-relay. Put the article on it, from examples/reader/go:

terse put ../hello.txt --relay ws://127.0.0.1:7979
terse: taken by 1 of 1 relays: ws://127.0.0.1:7979
e01027372f56996fa53fde7ae45aed656e196ccb4e7d79d3b66a51d9590be3a8

The last line is the article's ID. terse hash prints the same ID without asking a relay, which saves typing it:

go run ./fetch ws://127.0.0.1:7979 $(terse hash ../hello.txt)

It prints the article exactly as step 1 did. Ask for a blob the relay does not hold, such as go.mod, and it says so:

go run ./fetch ws://127.0.0.1:7979 $(terse hash go.mod)
2026/11/21 23:22:50 the relay does not have it
exit status 1

log.Fatal puts the date and time before the message, and go run adds the exit status.

What it leaves out

The program asks one relay and keeps nothing. A complete reader keeps every blob it fetched, so that an article opens at once the next time with no network at all, asks several relays, and matches replies to requests by their numbers. In tersereader that is internal/client/client.go, with the store in internal/store/store.go. A reader may also leave all of the network to a node, a separate program it asks over a local socket; Writing a reader without the machine says how.

What you have now

A reader that fetches an article by its ID and knows it is genuine.
