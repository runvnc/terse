# The Terse32 machine

This article describes machine profile 1, the only profile so far: the
CPU, the memory map, how frames and the budget work, how a machine stops,
the image file a program is shipped in, and how programs call devices.
The complete table of calls is an article of its own, linked under "Call
table" below. Each device's calls are described in full in that
device's article.

The machine is the optional third layer of Tersenet: the network and the
article format are the core, and a reader can implement them without
it. Which devices a host provides (the reading and the program profile)
and how a program does without some is in
[the system device](terse:65aa289e4c4fe3a2fffe74d82470b46ea37d343e88af96407cb5d0ae48314723).

## CPU

The CPU executes exactly RV32I with the M (multiply and divide) and C
(compressed) extensions, little-endian, in user mode. There is no A, F, D
or B extension, no Zicsr or Zifencei, and no privileged architecture: no
control and status registers, counters or traps are visible.

| Instruction | Behaviour |
|---|---|
| `FENCE` (funct3 = 0, including `FENCE.TSO`, `PAUSE`, hint forms) | does nothing |
| HINT encodings (`c.addi x0, 5`, `slli x0, x0, 3`, ...) | execute as written; writes to `x0` are discarded |
| `div`, `divu` by zero | give all ones; no trap |
| `rem`, `remu` by zero | give the dividend |
| `div` of −2³¹ by −1 | gives −2³¹; `rem` gives 0 |
| jumps and branches | targets need only be even; `jalr` clears bit 0 |
| loads and stores | must be aligned to their size (2 or 4), else a misaligned fault |
| `ecall` | a device call (see Calls below) |

A jump to an address outside ROM and RAM faults when the instruction there
is fetched, not at the jump. Everything else faults as an illegal
instruction: `ebreak` and `c.ebreak` (a breakpoint fault); every reserved
or illegal encoding, including the all-zero parcel `c.unimp`,
`C.ADDI4SPN`, `C.ADDI16SP` and `C.LUI` with a zero immediate, `C.LWSP` and
`C.JR` with register 0, compressed shifts with shamt[5] set, `C.SUBW`,
`C.ADDW` and the reserved MISC-ALU codes, every compressed floating-point
load or store, all 48-bit and longer encodings, CSR instructions,
`FENCE.I`, `MRET`, `WFI` and the other privileged encodings.

## Memory map

| Address | Contents | Access |
|---|---|---|
| `0001_0000h` to `0001_0000h` + rom_len − 1 | ROM: the image's bytes | read, execute |
| `0010_0000h` to `0010_0000h` + 8,192 × ram_pages − 1 | RAM | read, write, execute |
| everything else | nothing | any access faults |

So address 0 faults, a store to ROM faults, and so does fetching an
instruction any part of which lies outside ROM and RAM (for example a
32-bit instruction whose second half would be past the end of ROM). Code
may run from RAM; an instruction fetched from RAM is decoded when it is
executed, so code written to RAM takes effect at once, but each such
instruction costs 4 units instead of 1.

ROM is at most 262,144 bytes, so it ends by `0005_0000h`; RAM is at most
96 pages, so it ends by `001C_0000h`: ROM and RAM together are at most 1
MiB. Both start at the same address whatever their size, and a program's
addresses depend only on its own `ram_pages`.

## Reset state

- `pc` = `0001_0000h`, the first byte of ROM.
- `sp` (`x2`) = `0010_0000h` + 8,192 × ram_pages, the end of RAM. Every
  other register is zero.
- All RAM is zero, every device is in its reset state, the budget is zero
  and the frame counter is 0.

## Frames and the budget

Time advances in frames, nominally 60 a second. There are no interrupts.
For each frame the host does, in order:

| Step | What happens |
|---|---|
| 1 | appends the frame's input events to the event queue, latches the clock, the random bytes and the controllers, and applies the content completions it has for this frame (their content-done events come after the input events) |
| 2 | adds 125,000 to the budget, subtracts the charge for the content delivered in step 1, and runs the CPU while the budget is greater than zero |
| 3 | ends the frame: the frame counter increases by one, and the host presents the terminal, the vector displays and the page as they are now |

| Rule | Detail |
|---|---|
| Instruction cost | 1 unit fetched from ROM, 4 fetched from RAM |
| `ecall` cost | 1 (or 4 from RAM) plus the call's charge |
| Overrun | an instruction that starts with a positive budget runs to completion, so the budget can end below zero |
| Negative carry | a negative remainder carries into the next frame; if it exceeds a whole frame's budget, that frame runs nothing and the rest carries on |
| No positive carry | unused budget never carries forward |
| Running out | the machine pauses and continues with the next instruction in the next frame; the program is not told |
| `wait_frame` | the rest of the budget is discarded and the call returns at the start of the next frame, which always runs (content delivered in a frame costs at most 32,768 units) |
| Stopping | `exit` or a fault stops the machine at once; the rest of the budget is dropped, the frame still counts, nothing runs later |

A host that falls behind real time lets virtual time lag; it never runs
extra frames to catch up. In a system of several machines each machine has
its own budget, carry and frame counter.

## Stopping and faults

A machine is running, or stopped by an exit or a fault. A fault has no
exit code, and a host must show a fault as a fault, with its kind and
addresses. The faulting instruction is not executed and not charged, and
`pc` is left pointing at it.

| Stopped | Cause | Recorded |
|---|---|---|
| Exit | the `exit` call | the exit code, 0 to 255 |
| Fault | one of the kinds below | the kind, `pc` and an address |

| Number | Fault kind | Cause | Address recorded |
|---|---|---|---|
| 1 | Illegal instruction | a reserved, illegal or unsupported encoding; the 16- or 32-bit encoding is recorded too | `pc` |
| 2 | Breakpoint | `ebreak`, `c.ebreak` | `pc` |
| 3 | Fetch | an instruction, or its second half, is not in ROM or RAM | the address that could not be fetched |
| 4 | Load | a load from outside ROM and RAM | the load address |
| 5 | Store | a store outside RAM (ROM included) | the store address |
| 6 | Misaligned | a load or store not aligned to its size | the access address |

The numbers are those of the state serialization and of the shell's
`info` record.

## The image format

A program is one file (suggested extension `.terse`): a 32-byte header,
the device entries, then the ROM. All numbers are little-endian.

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | Magic: `54h 45h 52h 53h` (`TERS`) |
| 4 | 1 | Format version: 0 |
| 5 | 1 | Machine profile: 1 |
| 6 | 3 | `rom_len`: 1 to 262,144 |
| 9 | 1 | `ram_pages`: 8 KiB pages of RAM, 1 to 96 |
| 10 | 1 | `n_dev`: device entries, 0 to 16 |
| 11 | 5 | Reserved, zero |
| 16 | 16 | Title, UTF-8, padded with `00h` |
| 32 | 2 × `n_dev` | (device slot, version byte) pairs |
| 32 + 2 × `n_dev` | `rom_len` | ROM; byte 0 is at `0001_0000h` |

- The file length must be exactly 32 + 2 × `n_dev` + `rom_len`.
- The image ID is the BLAKE3-256 hash of the whole file. It names the
  program everywhere: an image is a blob, and its ID is its blob ID.
- A version byte is the device's version (0 to 127), with the top bit
  (`80h`) set if the device is optional. A slot may be listed at most
  once. Devices 1 and 8 are never optional; device 1 is always present.
- The title is the 16 bytes without their trailing `00h` bytes. Hosts do
  not check it (`terse pack` refuses one that is not UTF-8); a built-in
  whose title is not a valid display name cannot be started by name,
  only by its image ID.
- A host refuses an image whose profile or required device versions it
  does not implement (also when a shell starts it). An optional device it
  lacks, like a device not listed, is absent: its calls return
  `FFFF_FFFFh`.
- `terse pack --rom <bin> --title <t> --ram-pages <n> --device 2:0
  --optional 4:0 -o <out>` builds an image: `--device S:V` per required
  device, `--optional S:V` per optional one.

| Slot | Device | Version | In profile |
|---|---|---|---|
| 1 | System | 0 | reading, program |
| 2 | Terminal | 0 | reading, program |
| 3 | 2D vector display | 0 | program |
| 4 | Content | 0 | reading |
| 5 | Messages | none | reserved |
| 6 | Sound | 0 | none |
| 7 | Page | 0 | reading |
| 8 | Machines | 0 | none: the shell of a system only |
| 9 | 3D vector display | 0 | none |
| 10 | Full text (no calls) | 0 | reading |

Slots 0 and 11 to 239 are not devices; 240 to 255 are for experimental devices.

## Calls

A program reaches a device with `ecall`. Register `a7` holds the call
number, (device slot << 8) | function; arguments are in `a0` to `a5`; the
result is in `a0`, and a second result in `a1` where listed. A call
changes no other register and no memory but the buffers it is said to
write; `pc` continues after the `ecall`.

- An unknown call, or a call to a device the machine does not have, returns
  `FFFF_FFFFh` (`TERSE_ERR_UNKNOWN`) and does nothing else.
- A buffer is a pointer and a length. A buffer a device reads must lie
  wholly in ROM or wholly in RAM; one it writes must lie wholly in RAM. A
  buffer of length 0 is valid at any address, for every call. Otherwise
  the call returns `FFFF_FFFEh` (`TERSE_ERR_BUFFER`) and does nothing
  else. This is not a fault.
- Exceptions: a vector display list not wholly in RAM is rejected (result
  1, as for a bad length); a content request block not in RAM is rejected
  with handle 0, and a data range of the block that is not where it must
  be makes the request invalid (status `04h`); page `submit` returns 1
  for a bad length before it looks at the buffer.
- A call checks its buffer before its other arguments: a bad buffer gives
  `FFFF_FFFEh` whatever they are (page `submit` aside).
- Buffers need no alignment. Every call is charged, also when it fails:
  see [charges](terse:700aa265f5d0ae8141b841e6eeecb0b6146ac6935da3121441ee039db69ecf7c).

In C, `terse.h` has a constant for every call (`CALL_WAIT_FRAME`, ...)
and the inline functions `terse_call`, `terse_call4`, `terse_call5` and
`terse_call2` (for two results).

## Screen units

Every device that draws, and the pointer, uses one coordinate system: the
screen is 640 units wide and 480 high, (0, 0) at the top left, x to the
right and y down. Units are square; the host shows the screen at a 4:3
shape, so a circle is round. A terminal cell is 8 units wide and 16 high:
the cell at (column, row) starts at x = column × 8, y = row × 16. The
vector displays use sixteenths of a unit for finer positions.
